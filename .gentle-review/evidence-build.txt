Behavioral rationale: on device the previous release printed exactly one scheduling line (cierre agendado en 500 ms) and then, on every subsequent event, only the end-of-pass line, with no timer output of any kind. Two hypotheses fit: the pendingCloseId was never reset (the postDelayed runnable never executed) or the re-read exited through the silent continue when the parsed id differed from the scheduled id (parseOrder keeps the last ID node, and app-mode windows can restructure between detection and the 500 ms re-read). The fix instruments every stage of the timer lifecycle so the next logcat run distinguishes them (branch skip reasons, timer entry, per-window re-read with id and offer marker, completion before reset) and removes the silent path by deciding closure on the product rule: an offer popup with no Cruz Verde service node closes regardless of the parsed id. The service-node re-check at 500 ms is preserved, so a Cruz Verde order that finished rendering is still skipped with a log.
