4. Behavioral rationale: the user reports Picap emits a very high number of accessibility events, each currently triggering a full EVENT_DEBUG line plus a logWindows() dump plus a tree re-read. The requested behavior is: detect the high rate, limit processing to 1 event per second during the burst, and restore normal processing when the rate drops. Implementation: every Picap arrival increments a 1 s window counter (arrivals are counted even when the event itself is discarded, so the detector never starves); above 8 events/s the throttle activates immediately (Log.i entry with rate); while active, at most one event per 1000 ms proceeds to the normal pipeline (EVENT_DEBUG, logWindows, handlePicapEvent), the rest are counted silently (picapEventsDropped) to avoid replacing the flood with a log flood; only when a complete window drops to 4 events/s or fewer does the throttle deactivate (Log.i exit with the discarded count). Safety of discarding: handlePicapEvent re-reads the window tree (findAllWindows + parseOrder) rather than consuming the event payload, so no state is lost - worst case is up to 1 s of extra detection latency for a newly rendered popup, and the NO-CV close pipeline is untouched. Non-Picap events (WhatsApp, system) take the original code path byte-for-byte.
